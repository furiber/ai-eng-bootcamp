# Week 2 Assignment — Ask API

A FastAPI service with one endpoint, `POST /ask`, that sends a question to an
OpenAI model and returns a **typed, structured answer** alongside its token,
latency and cost figures. A static single-page frontend is served from the same
app, so there is one container and no CORS configuration.

This is a separate service from `ask-api` at the repository root and from
`week-1-assignment` beside it. It begins as a copy of the Week 1 service — the same
typed `/ask` endpoint — and Session 2 builds retrieval on top of it. All three
deploy independently.

Not deployed yet. See [Deploy to Render](#deploy-to-render) below — the blueprint
entry exists, but the service has not been created.

The Week 1 service it was copied from is live at
<https://week-1-assignment-65md.onrender.com>.

| Path            | What it is                                    |
| --------------- | --------------------------------------------- |
| `/`             | Frontend page that calls the API              |
| `/ask`          | The endpoint (POST JSON)                      |
| `/ingest`       | Chunk and index a document (POST JSON)        |
| `/debug/retrieve` | Retrieval on its own, no LLM (GET)          |
| `/health`       | Liveness probe, used by Render's health check |
| `/docs`         | Swagger UI (generated by FastAPI)             |
| `/redoc`        | ReDoc, same schema                            |
| `/openapi.json` | The OpenAPI schema itself                     |

## The response shape

`model` is optional and falls back to `DEFAULT_MODEL`:

```bash
curl -X POST http://127.0.0.1:8000/ask \
  -H "Content-Type: application/json" \
  -d '{"question": "What is RAG?", "model": "gpt-4o-mini"}'
```

```json
{
  "answer": {
    "answer": "Passwords must be at least 14 characters and rotated every 90 days. ...",
    "confidence": 0.9,
    "sources_needed": false,
    "citations": ["doc3_security"]
  },
  "model": "gpt-4o-mini-2024-07-18",
  "retrieved_chunk_ids": [
    "doc3_security#1", "doc3_security#11", "doc3_security#3",
    "doc3_security#0", "doc1_handbook#15"
  ],
  "tokens_used": 1143,
  "latency_ms": 2624,
  "cost_usd": 0.000209
}
```

`retrieved_chunk_ids` is everything that was put in front of the model, in rank
order. `answer.citations` is the subset the model says it actually used, given
as `document_id`s. The two differing is normal and useful: five chunks retrieved
and one document cited means retrieval cast a wide net and generation was
selective.

`top_k` is a request field, default 5, range 1–50.

The nested `answer` object is what makes this endpoint a component rather than a
chat wrapper: `client.chat.completions.parse` constrains the model to that Pydantic
schema, and the result is validated again before it is returned. A refusal or
unparseable output becomes a `502`, never a `200` with empty content.

`latency_ms` now covers retrieval **and** generation, since that is what the
caller waited for. In Session 1 it wrapped the single model call.

`tokens_used` and `cost_usd` remain generation figures, unchanged in meaning
from Session 1. The embedding call made to retrieve is not priced in: there is
no embedding entry in `MODEL_PRICES_PER_1K`, and quietly folding a partial
figure into a field that has always meant generation is worse than leaving it
alone. At `text-embedding-3-small` rates a question costs well under a
millionth of a dollar to embed, so the omission is small — but it is an
omission, not a rounding.

## Grounding

`/ask` answers **only** from retrieved context. The contract lives in
`GROUNDING_SYSTEM_PROMPT` in `main.py`, as a module constant rather than inlined
in the handler — a prompt is behaviour, and behaviour that exists only inside an
f-string is behaviour nobody reviews.

The five rules it sets: answer only from the context; cite the `document_id` of
each chunk used, not every chunk shown; refuse and set `sources_needed` when the
context is insufficient; treat `confidence` as context support rather than
plausibility; never mention the retrieval process.

Each chunk reaches the model as:

```
[1] document_id: doc3_security | source: doc3_security.txt
Passwords must be at least 14 characters and rotated every 90 days.
```

The `document_id` is given plainly rather than left inside the chunk id, so the
model never has to parse `doc3_security#1` to work out what to cite.

Refusal is verifiable rather than assumed. Asked "What is the capital of
France?" — which the model certainly knows — against this corpus it returns:

```json
{
  "answer": "The context does not provide information about the capital of France.",
  "confidence": 0.0,
  "sources_needed": true,
  "citations": []
}
```

Retrieval still returns five chunks for that question, because a vector search
always returns its nearest neighbours however far away they are. Low scores are
not a filter — the refusal comes from the prompt, not from an empty result.

An empty index takes the same path: the context block reads `(no matching
documents were retrieved)` and the answer comes back as a refusal in the usual
shape, so a caller has no special case to handle.

`cost_usd` is an **estimate**. Prices are hardcoded in `MODEL_PRICES_PER_1K` in
`main.py` (list prices as of 2026-08-18) and OpenAI can change them at any time.
The API reports a dated model id such as `gpt-4o-mini-2024-07-18`, so pricing
falls back to the longest matching prefix. A model with no price on file returns
`"cost_usd": null` rather than a figure derived from the wrong rates — a wrong
number is worse than an absent one.

## Error handling

| Situation                              | Status | Body                                    |
| -------------------------------------- | ------ | --------------------------------------- |
| Empty or oversized `question`          | 422    | FastAPI validation detail               |
| Unknown model name, upstream bad request | 400  | The provider's message                  |
| `OPENAI_API_KEY` not configured        | 500    | `OPENAI_API_KEY is not configured`      |
| Refusal, unparseable or invalid output | 502    | The refusal text or validation error    |
| Upstream auth, quota or outage         | 502    | `OpenAI error: …`                       |

An unknown model is worth calling out, because the obvious guess is wrong. The
SDK raises `openai.NotFoundError` (**404 `model_not_found`**) for it, not
`BadRequestError`, so catching only `BadRequestError` would miss it entirely.
Both upstream `400` and `404` are treated as a bad request from the caller and
answered with a `400`:

```json
{ "detail": "The model `gpt-nonexistent-9000` does not exist or you do not have access to it." }
```

Everything else from the provider stays a `502`. A quota or auth failure is not
the caller's to fix, so it should not be reported as their mistake.

## Run locally

```bash
python -m venv .venv

pip install -r requirements.txt

```

Open <http://127.0.0.1:8000/> for the frontend or <http://127.0.0.1:8000/docs>
for Swagger UI.

**This folder has its own `.env`.** Copy the template and fill it in:

```bash
cp .env.example .env
```

`env_setup.py` loads that file and only that file — this service does not read
the repository root's `.env`. Confirm the key is found without printing it:

```bash
python env_setup.py
```

`.env` is both gitignored and `.dockerignore`d, so it reaches neither the repo nor
the container image. Render supplies the same variable names as real environment
variables instead.

`.env.example` documents every variable the service reads:

| Variable               | Secret | Default                  | What it does                                          |
| ---------------------- | ------ | ------------------------ | ----------------------------------------------------- |
| `OPENAI_API_KEY`       | yes    | —                        | Chat completions and embeddings                       |
| `PINECONE_API_KEY`     | yes    | —                        | The vector store                                      |
| `DEFAULT_MODEL`        | no     | `gpt-4o-mini`            | Model used when a request omits one                   |
| `EMBEDDING_MODEL`      | no     | `text-embedding-3-small` | Used at both ingest and query time — never split them |
| `EMBEDDING_DIMENSIONS` | no     | `1536`                   | Must equal the index's dimension                      |
| `PINECONE_INDEX_NAME`  | no     | `ask-api-docs`           | Which index to read and write                         |
| `PINECONE_CLOUD`       | no     | `aws`                    | Index creation only                                   |
| `PINECONE_REGION`      | no     | `us-east-1`              | Index creation only                                   |
| `CHUNK_SIZE`           | no     | `800`                    | Chunk length in characters, not tokens                |
| `CHUNK_OVERLAP`        | no     | `100`                    | Overlap in characters; must be smaller than the size  |

Only the two keys are secret. Every default above is applied in code, so a
`.env` holding just the two keys is enough to run locally.

## Indexing a document

`POST /ingest` chunks a document, embeds each chunk and stores it.

```bash
curl -X POST http://127.0.0.1:8000/ingest \
  -H "Content-Type: application/json" \
  -d '{
        "document_id": "handbook-2026",
        "text": "Retrieval-augmented generation combines a retrieval step with a generative model. ...",
        "metadata": {"source": "handbook.md"}
      }'
```

```json
{ "document_id": "handbook-2026", "chunks_indexed": 1, "status": "indexed" }
```

`chunks_indexed` follows the length of the text: roughly one chunk per
`CHUNK_SIZE` characters. The short sample above is a single chunk; a 3,000
character document comes back as five.

`metadata` is optional and free-form, but values must be strings — Pinecone
accepts only strings, numbers, booleans and lists of strings, so the request
model restricts it rather than letting a nested object fail at upsert time.
`source` is pulled out by name so every chunk carries the key whether or not
the caller supplied it; anything else is stored alongside untouched.

Each chunk is stored under `<document_id>#<chunk_index>` with metadata
`document_id`, `chunk_index`, `source` and the chunk `text`. Those ids are
deterministic, so **re-sending the same `document_id` overwrites its chunks
rather than duplicating them** — the endpoint is safe to retry.

A document that has since got *shorter* also has its surplus tail chunks
removed: upserting only overwrites the ids being rewritten, so the orphans of a
longer previous version would otherwise linger and keep matching searches. The
cleanup runs after the write, never before, so a failed upsert cannot take the
previous version's chunks with it.

### Chunking

`RecursiveCharacterTextSplitter` splits on the largest natural boundary that
fits — paragraphs, then lines, then words, then raw characters — so a chunk
breaks between ideas rather than mid-word where it can.

`CHUNK_SIZE` and `CHUNK_OVERLAP` are counted in **characters, not tokens**: the
splitter measures with `len()`. The overlap carries the tail of one chunk into
the next, so a sentence spanning a boundary is still retrievable from one side
of it.

The splitter is built on first use rather than at import. Its constructor
raises when the overlap is not smaller than the chunk size, and both values come
from the environment — at import time a bad setting would stop the app booting
and take `/health` down with it. Deferred, it is a `500` on `/ingest` naming both
variables, and `/health` keeps answering.

### Errors

| Situation                                  | Status |
| ------------------------------------------ | ------ |
| Empty or whitespace-only `text`            | 400    |
| Blank `document_id`                        | 400    |
| Text that produces no chunks               | 400    |
| Document too large for one embedding batch | 400    |
| `text` over 200,000 characters             | 422    |
| Missing `OPENAI_API_KEY` or `PINECONE_API_KEY` | 500 |
| `CHUNK_OVERLAP` not smaller than `CHUNK_SIZE`  | 500 |
| Upstream auth, quota or outage             | 502    |

Empty input is a `400` rather than the `422` a `min_length` constraint would
produce, which is why the field carries no minimum and the handler checks it.

Indexing nothing is also a `400`. A `200` reading `"chunks_indexed": 0` would
look like the document was stored.

## Loading the sample corpus

`ingest_docs.py` walks a directory of `doc*.txt` files and posts each one to
`/ingest`. The API must already be running.

```bash
uvicorn main:app --reload              # terminal 1
python ingest_docs.py --fresh          # terminal 2
```

```
emptied ask-api-docs

document_id  file                           chunks
--------------------------------------------------
POL-101      doc1_handbook.txt                  22
POL-114      doc2_expenses.txt                  12
POL-207      doc3_security.txt                  12
SPEC-WB9     doc4_product.txt                   11
POL-220      doc5_it_acceptable_use.txt          4
POL-118      doc6_facilities.txt                 4
--------------------------------------------------
             indexed this run                   65
             in the vector store                65
```

The two totals should match. They differ when something else is still in the
index — an earlier document under a different id, or a manual test vector.

`--fresh` empties the index first. Without it, documents are overwritten in
place and anything else present is left alone.

The default directory is `~/ai-eng-bootcamp-resources/RAG/northwind-sample-docs`;
pass another path as the first argument.

### Where the document_id comes from

From each file's own `Document ID:` header (`POL-101`), not its filename. That
is what makes re-running the script overwrite the same chunks rather than write
a second copy — an id derived from a filename changes the moment the file is
renamed.

The parsing lives in the script, not in `/ingest`. A header convention that
holds for these six files should not become an API rule; the endpoint stays
agnostic about where a caller's `document_id` comes from.

It raises rather than falling back to the filename when the header is missing.
A fallback writes chunks under an id nobody expects and nothing complains until
a citation reads wrong.

**Renaming a document_id is a delete-then-ingest, not a re-ingest.** The
stale-chunk cleanup inside `ingest_document()` only finds orphans sharing the
same `document_id`; change the id and every chunk id changes with it, so the old
vectors survive as a duplicate copy of the corpus under the old name. That is
what `--fresh` is for.

## Checking retrieval on its own

`GET /debug/retrieve?q=...` embeds a question and returns the nearest chunks
with their scores and metadata. **No LLM is called and no answer is generated**,
so it shows exactly what a prompt would be built from — which is the thing to
get right before generation is wired in at all.

```bash
curl -s -G "http://127.0.0.1:8000/debug/retrieve"   --data-urlencode "q=How do I claim travel expenses?" --data-urlencode "top_k=3"
```

```json
{
  "question": "How do I claim travel expenses?",
  "matches": [
    {
      "id": "doc2_expenses#3",
      "score": 0.659,
      "document_id": "doc2_expenses",
      "chunk_index": 3,
      "source": "doc2_expenses.txt",
      "text": "Travel over 50 miles may be claimed at 45 pence per mile. ..."
    },
    {
      "id": "doc2_expenses#2",
      "score": 0.639,
      "document_id": "doc2_expenses",
      "chunk_index": 2,
      "source": "doc2_expenses.txt",
      "text": "Personal cards vs company cards. Prefer a company card when issued. ..."
    }
  ]
}
```

`top_k` defaults to 5 and accepts 1–50. Scores are cosine similarity: higher is
closer, 1.0 is identical.

Judge the **gap**, not the absolute number. Ordinary prose against a real corpus
scores in the 0.4–0.7 range, and a near-verbatim match against a one-line
document scores far higher; neither figure means much alone. What matters is
whether the right chunks sit clearly above the wrong ones. Scores bunched
together mean the embeddings are not separating your content, and no amount of
prompt work downstream fixes that.

Read the whole `text` of a match before concluding retrieval missed. A chunk is
up to `CHUNK_SIZE` characters and the passage that answers the question is often
well past its opening line, so a short preview can hide a correct hit.

No matches is a `200` with an empty list, not a `404`. Nothing indexed yet is a
real answer and the exact thing this endpoint exists to reveal. A blank `q` is a
`400`.

**This reads out indexed content to anyone who can reach it.** Fine locally.
Think before leaving it reachable on a public deployment — there is no auth on
it, and `/ingest` has none either.

## Vector store (Pinecone)

`rag.py` owns embeddings and the vector store, so `main.py` stays the HTTP
layer. Nothing is constructed at import time: the module can be imported with no
credentials at all, which is what keeps the app booting and `/health` answering
on a deploy where a key is missing.

Confirm Pinecone is reachable. It makes no OpenAI call, so it costs nothing, and
it prints key lengths rather than key values:

```bash
python rag.py
```

```
index:      ask-api-docs
embedding:  text-embedding-3-small @ 1536 dims
PINECONE_API_KEY found: True (length 75)
reachable:  yes (state Ready, ready True)
dimension:  1536, vectors: 0
```

The same check is importable as `rag.check()`. It exits non-zero on failure, so
it also works as a startup gate in a shell script.

It reports a **dimension mismatch as a failure**, not a warning. A mismatch
between the index and `EMBEDDING_DIMENSIONS` is accepted silently at config time
and only surfaces later as every upsert being rejected.

If the index does not exist yet, create it once:

```bash
python -c "import rag; rag.ensure_index()"
```

That is a real resource on your Pinecone account. It is not called automatically
on startup — a web service quietly creating cloud infrastructure when it boots
is a surprise nobody wants at 3am.

### The one rule that matters

**Ingest and query must embed identically.** Vectors produced by different
models — or the same model at different dimensions — are not comparable, and
mixing them does not raise: searches just return quietly wrong results. So
`embed()` is the single entry point both paths go through, reading one
`EMBEDDING_MODEL` and one `EMBEDDING_DIMENSIONS`. `test_rag.py` asserts the two
paths send identical values.

If you ever change either setting, the existing vectors are stale. Re-ingest
everything into a fresh index rather than mixing generations in one.

### What it does not do

`/ask` does not retrieve yet. Documents go in through `/ingest`, and
`/debug/retrieve` shows what would come back for a question, but nothing wires
those matches into the prompt — that is the next step.

## The Streamlit page

An optional local UI over the same endpoint. It needs two terminals, because the
API and the page are separate processes:

```bash
uvicorn main:app --reload          # terminal 1
streamlit run streamlit_app.py     # terminal 2
```

Open <http://localhost:8501>. The sidebar takes the API base URL, so the page can
be pointed at the deployed service instead of a local one. It shows confidence,
tokens, latency and cost; an unpriced model reads `unpriced` rather than
`$0.000000`, which would look like a free call.

## Deploy to Render

The blueprint lives at the repository root in `render.yaml`, which defines this
service alongside `ask-api` and `week-1-assignment`. This one sets
`rootDir: week-2-assignment`, so the build context and Dockerfile both come from
this folder, and a `buildFilter` on `week-2-assignment/**` keeps commits
elsewhere in the repo from rebuilding it.

Render prompts for `OPENAI_API_KEY` and `PINECONE_API_KEY` on the first deploy —
both are marked `sync: false`, so neither value ever lives in the repo. The five
non-secret settings are declared with literal values in the blueprint instead,
so they are visible and reviewable in the diff.

The index itself is not created by the deploy. Run `ensure_index()` once against
the same credentials before the service needs to serve a query. The container binds
`0.0.0.0:$PORT`, which Render requires, and `/health` is the health check path.

## Gotchas

The `StaticFiles` mount at `/` is a catch-all and **must stay the last route
registration** in `main.py`. Move it above the route decorators and `/health`,
`/ask`, `/docs` and `/openapi.json` all become 404s. `test_main.py` covers this.

The OpenAI client is constructed at import time with whatever `OPENAI_API_KEY`
holds, using a placeholder string when it is absent — `openai>=3` raises at
construction when no key can be found, including for an explicit `api_key=None`.
The `/ask` handler checks the key itself and returns a clear `500`. This is
deliberate: the app must boot and pass `/health` without a key, so a Render
container-start failure stays readable. Do not move the check to import time.

If `/` returns 404 while `/health` still answers, an older uvicorn process is
holding the port and serving stale code. Check what it actually exposes, then
kill it:

```bash
curl -s http://127.0.0.1:8000/openapi.json   # should list /health and /ask
```

```powershell
Get-CimInstance Win32_Process -Filter "Name='python.exe'" |
  Where-Object { $_.CommandLine -like '*uvicorn*' } |
  ForEach-Object { Stop-Process -Id $_.ProcessId -Force }
```
